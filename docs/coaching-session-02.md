# MarginSight สำหรับ AWS Cloud Coaching

### เอกสารเตรียมทีมสำหรับ Coaching Session 02 กับ NTT DATA Thailand

อัปเดต 15 ตุลาคม 2026 | ใช้อ่านก่อนคุยและนำไปให้ AI สรุปต่อ

MarginSight ช่วยร้านค้าเล็กดูว่าขายแล้วเหลือกำไรเท่าไร โดยนำเข้ารายงานสินค้า ต้นทุน ออเดอร์ และรายการเงินหัก แล้วแสดงกำไร margin และ TTR พร้อมที่มาของตัวเลข ทีมมีเว็บและบริการ AWS ที่ deploy แล้ว ใช้ข้อมูลจำลองสำหรับสาธิต และยังมีส่วนที่ต้องทดสอบกับข้อมูลร้านจริง

### ประเด็นที่ต้องตอบให้ชัด

ผู้ช่วยและการอ่านภาพบิลใช้ Amazon Nova Lite ผ่าน Amazon Bedrock รุ่น amazon.nova-lite-v1:0 เรียกแบบ inference ยังไม่ได้เทรนหรือ fine-tune เพิ่มด้วยข้อมูลร้าน ส่วนกำไรคำนวณด้วยโปรแกรมที่ตรวจสอบสูตรและหน่วยเงิน ไม่ใช่ตัวเลขที่ให้โมเดลเดา

### สคริปต์อธิบายสั้นสำหรับพูดเปิด

“เราใช้ AWS แบบ serverless เพื่อประหยัดเครดิต ร้านนำเข้าไฟล์ CSV หรือ XLSX แล้ว Lambda ประมวลผลผ่านคิวและเก็บข้อมูลใน DynamoDB ผู้ช่วยภาษาไทยใช้ Nova Lite เพื่อเข้าใจคำถามและเรียกเครื่องมือคำนวณ ส่วนภาพบิลใช้โมเดลอ่านเป็นร่างให้คนยืนยันก่อนบันทึกต้นทุน ตอนนี้ยังไม่ฝึกโมเดลเพิ่ม เรากำลังเก็บชุดทดสอบที่มีเฉลยเพื่อวัดผลก่อนตัดสินใจเทรนครับ”

### ตัวอย่างที่อธิบายได้ว่าตัวเลขมาจากไหน

| รายการ MOCK ต่อออเดอร์ | จำนวน |
| --- | --- |
| รายรับสินค้า หลังส่วนลดผู้ขาย | 200.00 บาท |
| ค่าบริการที่บันทึก 24 + 16 + 6 | 46.00 บาท |
| ต้นทุนสินค้า / แพ็ก / โฆษณา | 130 / 5 / 10 บาท |
| กำไรส่วนที่บันทึก 200 - 46 - 130 - 5 - 10 | 9.00 บาท |
| Margin = 9 / 200 และ fee ratio = 46 / 200 | 4.5% และ 23% |
| TTR ในขอบเขตเดโม = (46 + 10) / 200 | 28% |

อัตราในตัวอย่างเป็น MOCK ไม่ใช่อัตราของ marketplace จริง TTR รุ่นนี้รวมค่าบริการกับโฆษณาที่บันทึก และประกาศขอบเขตแยกจากต้นทุนสินค้า ค่าแพ็ก ค่าส่ง และค่าใช้จ่ายประจำ ไม่ใช่ 100 ลบ margin

## แต่ละส่วนของโปรแกรมใช้ AWS อะไร

ตารางนี้อ้างอิงโค้ดและ infrastructure ของ MarginSight ไม่ใช่รายการบริการที่เสนอเพิ่ม ทุกเมนูใช้ระบบสิทธิ์ร้านร่วมกัน

| ส่วนของโปรแกรม | บริการที่ใช้ | หน้าที่ในระบบ |
| --- | --- | --- |
| เว็บและไฟล์หน้าเว็บ | Amazon S3 + CloudFront | เก็บ Next.js static export ใน bucket private และส่งหน้าเว็บผ่าน HTTPS |
| สมัครและล็อกอิน | Amazon Cognito | บัญชีผู้ใช้และ access token แบบ OAuth code + PKCE |
| รับคำขอจากหน้าเว็บ | API Gateway HTTP API | ส่งคำขอไป Lambda และตรวจ JWT ของเส้นทางร้านจริง |
| กำไร margin TTR และราคา | AWS Lambda | รัน deterministic domain engine เดียวกันทั้งเว็บและผู้ช่วย |
| สินค้า ต้นทุน และข้อมูลร้าน | Amazon DynamoDB | เก็บ SKU ประวัติต้นทุน สมาชิก กฎ ออเดอร์ และงานประมวลผล |
| ไฟล์ CSV XLSX และภาพบิล | Amazon S3 private | อัปโหลด/ดาวน์โหลดด้วย presigned URL หลังตรวจสิทธิ์ |
| นำเข้าข้อมูลจำนวนมาก | Amazon SQS + Lambda | ทำงานเบื้องหลัง แบ่งงานและป้องกันการนำเข้าซ้ำ |
| งานที่ retry ไม่ผ่าน | SQS dead-letter queues | พักงานที่ retry แล้วยังไม่ผ่านไว้ให้ตรวจและกู้คืน |
| ผู้ช่วยร้านค้าภาษาไทย | Lambda + Amazon Bedrock | Nova Lite เข้าใจคำถาม เรียก tools และอธิบายผลจาก engine |
| อ่านบิลซื้อและตรวจร่าง | S3 + SQS + Lambda + Bedrock | อ่านภาพเป็น JSON ตรวจโครงสร้าง ให้ร้านยืนยันก่อนสร้าง cost version |
| กระทบยอดและส่งออก | Lambda + DynamoDB + S3 | เทียบ actual/estimate และสร้าง CSV/XLSX; ตัว parse XLSX ใช้ไลบรารีในโค้ด |
| LINE เมื่อมี Channel | Lambda + SQS + DynamoDB | ตรวจ signature ผูกสมาชิก และตอบผ่าน LINE API; live ยังขาด credentials |
| Log และการดูแลระบบ | CloudWatch Logs + IAM | เก็บ log ตาม retention และจำกัดสิทธิ์ execution roles |
| สร้างซ้ำและคุมงบ | SAM + CloudFormation + Budgets | นิยามทรัพยากรและติดตามงบแข่งขัน; budget ไม่ใช่ hard stop |

ระบบหลักอยู่ ap-southeast-1 ส่วน Bedrock เรียกตรง us-east-1 ตามขอบเขตที่อนุญาต CloudFront เป็น global ปัจจุบันไม่มี EC2/GPU, RDS, NAT Gateway หรือ SageMaker training job

## โมเดล AI และวิธีใช้งาน

### โมเดลที่ใช้งานจริง

ใช้ pre-trained Amazon Nova Lite รุ่น amazon.nova-lite-v1:0 ผ่าน Bedrock Converse API ทั้งผู้ช่วยและอ่านภาพ โมเดลรองรับข้อความและภาพ [1] เลือกใช้เพื่อทดลองงานหลายรูปแบบด้วยขอบเขตต้นทุนของต้นแบบ แต่ยังต้องวัดความแม่นยำภาษาไทยจากตัวอย่างของเราเอง

### ขั้นตอนของผู้ช่วยร้านค้า

คำถามภาษาไทย + SKU ที่เลือก + เดือน → โมเดลเลือก tool → โปรแกรมตรวจ arguments และสิทธิ์ร้าน → tool อ่านข้อมูลและคำนวณ → ส่งผลคำนวณให้โมเดลอธิบาย → ตรวจตัวเลขก่อนแสดง ถ้าคำตอบไม่ตรงหรือโมเดลล้มเหลว ใช้คำอธิบายจาก engine พร้อมแจ้ง fallback

Tools ปัจจุบันคือ getProfit, simulateDiscount, getBreakEven และ getCalculationEvidence เป็น orchestration ที่ทีมเขียนใน Lambda ไม่ใช่การ deploy บริการ Bedrock Agents หรือ Knowledge Bases. ตัวอย่าง “ลดสิบห้าเปอร์ยังไหวปะ” ต้องใช้ราคา/ต้นทุน/กฎของ SKU นั้น ไม่สร้างเปอร์เซ็นต์ค่าคอมเอง

### ขั้นตอนของการอ่านบิลซื้อ

ภาพ PNG/JPEG → private S3 → SQS → OCR worker → Nova Lite อ่านชื่อสินค้า จำนวน หน่วย ยอดต่อรายการ และยอดรวม → ตรวจ JSON/ยอด → แสดงร่าง → ร้านเลือก SKU และยืนยันจำนวนหน่วยต่อแพ็ก → โปรแกรมคำนวณต้นทุนต่อหน่วยขายและเก็บเวอร์ชันวันที่มีผล

คำว่า OCR ในระบบนี้หมายถึงอ่านเอกสารด้วย multimodal model ไม่ใช่ pipeline Textract ภาษาไทย เอกสาร Textract ที่ตรวจระบุภาษาอังกฤษ ฝรั่งเศส เยอรมัน อิตาลี โปรตุเกส และสเปน จึงยังไม่ควรอ้างว่ารองรับบิลไทยด้วย Textract [2]

### เทรนแล้วหรือยัง

| คำถาม | คำตอบสำหรับโครงการนี้ |
| --- | --- |
| AWS ฝึกโมเดลมาแล้วหรือไม่ | Nova Lite เป็นโมเดลสำเร็จรูปที่ผู้ให้บริการฝึกมาแล้ว |
| ทีมฝึกด้วยข้อมูลร้านแล้วหรือไม่ | ยังไม่เทรน ไม่ fine-tune และไม่มี training pipeline |
| ส่งข้อมูลเข้า prompt ถือว่าเทรนหรือไม่ | ไม่ใช่ เป็นบริบทเพื่อ inference รอบนั้น ไม่ได้ปรับน้ำหนักโมเดล |
| ข้อมูลร้านถูกนำไปฝึกโดยอัตโนมัติหรือไม่ | ทีมไม่ได้ตั้งการฝึกเพิ่ม; AWS ระบุว่า inputs/outputs ของ Bedrock ไม่ถูกใช้ฝึก Nova/Titan/โมเดล third-party [3] |

ทีมไม่ได้มีรายชื่อ corpus ทั้งหมดที่ผู้ให้บริการใช้ฝึกโมเดล จึงไม่ควรตอบว่าเราเทรนด้วยข้อมูล Shopee หรือใบเสร็จไทยจำนวนหนึ่งโดยไม่มีหลักฐาน

## ข้อมูลที่ต้องมีและหาได้จากไหน

### ข้อมูลสำหรับให้ระบบทำงาน

| ชุดข้อมูล | ฟิลด์สำคัญ | แหล่งที่ต้องใช้ |
| --- | --- | --- |
| สินค้าและต้นทุน | SKU ชื่อ หน่วย ต้นทุนต่อหน่วย วันเริ่มใช้ หลักฐาน | ไฟล์สินค้าของร้าน บิลซื้อ ใบเสนอราคา หรือ CSV ต้นทุนที่ร้านยืนยัน |
| ยอดขายและรายการเงินหัก | platform/order/transaction ID วันที่ จำนวน รายรับ ส่วนลด ค่าส่ง ค่าธรรมเนียม และ payout | รายงานออเดอร์และ statement ที่ร้านมีสิทธิ์ export; ยังไม่ดึง marketplace API อัตโนมัติ |
| กฎและการเข้าแคมเปญ | ฐานคิดเงิน VAT เพดาน หมวดสินค้า tier วันที่มีผล และสิทธิ์ร่วมโปรแกรม | เอกสารทางการ Seller Center หน้ายืนยันเข้าร่วม และ statement ร้านจริง |
| คำถามผู้ช่วย | ข้อความไทย SKU เดือน และผลจาก tools | ข้อความที่ผู้ใช้ถาม พร้อมข้อมูลร้านเฉพาะส่วนที่จำเป็นต่อคำถาม |
| บิลสำหรับ OCR | ภาพ วันที่ ชื่อ จำนวน หน่วย ราคา และเฉลยที่ตรวจแล้ว | ภาพสังเคราะห์สำหรับ demo; บิลร้านจริงต้องมีสิทธิ์ใช้และปกปิดข้อมูลที่ไม่จำเป็น |

ค่าบริการของแคมเปญไม่ได้มาจาก AI เดา ต้องทราบว่าร้านสมัครโปรแกรมใดและช่วงใด แล้วใช้รายการเงินหักจริงเป็นหลักเมื่อมี statement กฎประมาณการต้องมี version/source/effective date ข้อมูลขาดให้แสดงไม่ทราบ ไม่ใช้ 0 แทนข้อมูลที่ไม่มี

### ถ้ามี 1000 บิลหรือสินค้าหลายร้อยรายการ

ไม่ให้แม่ค้ากรอกทีละการขาย ใช้ CSV/XLSX สำหรับสินค้า ต้นทุน ออเดอร์ และค่าบริการ ระบบรับรายงานได้ครั้งละ 1000 แถว ต้นทุนใส่ต่อ SKU แล้วอัปเดตเมื่อเปลี่ยนหรือมีหลักฐานใหม่ ส่วน OCR ปัจจุบันรับภาพเป็นใบและต้อง review ไม่อ้างว่ามีการนำเข้า 1000 ภาพพร้อมกันแล้ว

### แยกข้อมูลใช้งาน ข้อมูลทดสอบ และข้อมูลฝึก

ข้อมูลใช้งานนำมาคำนวณของร้าน ข้อมูลทดสอบมีเฉลยใช้วัดว่าระบบทำถูกหรือไม่ ส่วนข้อมูลฝึกจะใช้ได้เมื่อได้รับสิทธิ์สำหรับการฝึกโดยเฉพาะ การที่ร้านอนุญาตให้คำนวณกำไรไม่ได้แปลว่าอนุญาตให้นำบิลไปฝึกโมเดล

ปัจจุบัน demo ใช้ MOCK และ golden cases ที่ทีมตรวจตัวเลขเอง มีการทดสอบ OCR จริงกับภาพบิลสังเคราะห์ 1 ภาพ จำนวนและยอดรวมตรง แต่ชื่อ/หน่วยผิด จึงยังไม่ใช่หลักฐานความแม่นยำกับบิลแม่ค้าจริง

## ถ้าจะเทรนเพิ่มและจะคุมค่าใช้จ่ายอย่างไร

### แผนข้อมูลสำหรับทดลองในอนาคต

เริ่มจากวัด baseline ของโมเดลเดิมและปรับ prompt/tools ก่อน ถ้ายังมีข้อผิดพลาดซ้ำที่ข้อมูลฝึกช่วยได้ จึงเลือกโมเดลและบริการปรับแต่งที่รองรับใน Region/งบขณะนั้น ยังไม่สร้าง training job หรือรับรองว่าจำเป็นต้อง fine-tune

| งาน | ข้อมูลและเฉลยที่ควรเก็บ | วิธีวัดผล |
| --- | --- | --- |
| เข้าใจคำถามร้านค้า | ตัวอย่างภาษาไทย/คำย่อ + intent + SKU/เดือน + tool arguments ที่ถูก; คำถามกำกวมมีเฉลยให้ถามกลับ | ความถูกต้อง intent/arguments การถามกลับ และอัตราตอบข้ามสิทธิ์ต้องเป็นศูนย์ในชุดตรวจ |
| อ่านบิลไทย | ภาพที่มีสิทธิ์ใช้ + เฉลยชื่อสินค้า จำนวน หน่วย ยอดต่อรายการ/รวม + การจับคู่ SKU ที่คนตรวจแล้ว | วัดแต่ละฟิลด์ ยอดเงินตรงถึงสตางค์ และอัตราที่คนต้องแก้; ไม่ใช้ความถูกยอดรวมแทนชื่อ/หน่วย |
| กำไรและราคา | golden cases ต้นทุนเก่า/ใหม่ fee cap VAT คืนสินค้า และรายการหักจริง | ต้องตรง engine/ledger ภายใต้นโยบายปัดเศษ ไม่ใช้ tolerance 5% กับยอด posted |

จำนวนเริ่มต้นที่เสนอเพื่อวัด baseline ไม่ใช่ข้อมูลที่เก็บแล้ว: คำถามไทย 200-300 ข้อ และบิลที่มีสิทธิ์ใช้ 100-200 ใบ ให้ร้าน/ผู้ตรวจทำเฉลย แบ่ง train/validation/test แยกตามร้านและเอกสารต้นฉบับ ไม่ให้ภาพใบเดียวกันหรือภาพดัดแปลงหลุดข้ามชุด

### หลักฐานและข้อจำกัดปัจจุบัน

43 tests ในเครื่องผ่าน พร้อม typecheck, build และ bundled Lambda. AWS เคยตรวจ health/private storage/import1000แถว/worker และบริการ AI ด้วย operator แล้ว แต่ยังไม่ใช่ทุก workflow ของร้านจริงหรือทุกคู่ผู้ใช้ LINE ยังไม่มี Channel credentials และ native marketplace adapter ยังต้องมี sample/schema/สิทธิ์จริง จึงใช้สถานะ PARTIAL_WITH_EXTERNAL_BLOCKERS

### ภูมิภาคและเครดิต

ใช้ทรัพยากร regional เฉพาะ us-east-1, ap-southeast-1, ap-southeast-7; ระบบหลัก Singapore และ AI direct us-east-1 ตามที่อนุญาต ไม่ใช้ Marketplace หรือ cross-region inference profile ที่อาจออกนอกขอบเขต เครดิตทีมรวม 350 USD ไม่ใช่รายเดือน เป้าหมายทดลอง25 USD ต้องดูยอดล่าสุดใน Budgets/Cost Explorer

ยอดที่อ่านได้ล่าสุดยังเป็น 0.008 USD จาก snapshot 15 ต.ค. 2026 เวลา 03:55 UTC จึงไม่รับรองว่าเป็นยอดปัจจุบันหรือเครดิตคงเหลือ คุมด้วย file/token/call/retry limits, SQS concurrency, TTL/lifecycle และ kill switch; budget เพียงอย่างเดียวไม่ใช่ hard financial cap

## คำตอบสั้นและคำถามที่จะคุยกับ Coach

### ใช้ AI รุ่นอะไร

Amazon Nova Lite amazon.nova-lite-v1:0 ผ่าน Amazon Bedrock Converse ทั้งผู้ช่วยและอ่านบิล เรียกตรง us-east-1

### ใช้ข้อมูลอะไรเทรน

ทีมยังไม่ได้เทรนเพิ่ม ข้อมูลร้านเป็น input เพื่อ inference และคำนวณ ข้อมูล MOCK/เฉลยเป็นชุดทดสอบ ไม่ใช่หลักฐานว่า fine-tune แล้ว

### ทำไมไม่ให้ AI คิด margin

ต้องอธิบายที่มาของทุกยอด มีต้นทุนและกฎตามวัน ค่าบริการจริงแทนประมาณการ และห้ามหักซ้ำ จึงให้ domain engine ทำเงินและให้โมเดลอธิบาย

### แม่ค้าต้องกรอกทุกออเดอร์ไหม

ไม่ต้อง ใช้รายงาน CSV/XLSX นำเข้าจำนวนมาก และอัปเดตต้นทุนต่อ SKU เฉพาะเมื่อเปลี่ยน ภาพบิลต้องตรวจร่างก่อนยืนยัน

### รู้ค่าคอมของแคมเปญจากไหน

จากหลักฐานเข้าร่วมและ statement ของร้าน ประกอบกับกฎทางการที่ตรวจวันมีผลแล้ว ถ้าหาไม่ได้ให้ UNKNOWN หรือใช้ MOCK ที่ติดป้าย

### ตอนนี้ยังขาดอะไร

ข้อมูลร้าน/รายงานที่ได้รับสิทธิ์ ชุดบิลไทยมีเฉลย การทดสอบ AWS กับผู้ใช้สองร้านครบ flow และ LINE Channel สำหรับ live check

### ประเด็นขอคำแนะนำจาก NTT DATA

1 วัดคุณภาพ Nova Lite กับบิลไทยอย่างไรในเครดิต 350 USD
2 ส่งภาพจาก Singapore ไป us-east-1 ควรปกปิดข้อมูลส่วนใด
3 ควรเพิ่ม quota หรือ kill switch และเฝ้าดูค่าใช้จ่ายตรงไหน
4 รายงานร้านจริงชุดแรกควรเริ่ม mapping/reconciliation ฟิลด์ใด
